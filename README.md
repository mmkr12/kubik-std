# KUBIK.std — Производство онлайн

Простая веб-платформа учёта заказов для рекламно-производственной компании KUBIK.
Next.js 14 (App Router) + TypeScript + TailwindCSS + shadcn/ui-style компоненты + Framer Motion + Supabase.

## Структура проекта

```
app/
  page.tsx                 — лендинг (hero, о компании, работы, калькулятор, контакты)
  production/page.tsx      — публичная страница "Производство онлайн" (все активные заказы)
  production/[id]/page.tsx — карточка заказа для клиента (эскиз, дата, статус)
  login/page.tsx           — вход для менеджеров
  admin/zamery/            — раздел "Замеры"
  admin/production/        — раздел "Производство" (кнопка ГОТОВО)
  admin/history/           — раздел "История" (поиск)
  admin/settings/          — раздел "Настройки" (цены, коэффициенты, КП)
  api/calculate/           — расчёт стоимости
  api/kp/                  — генерация коммерческого предложения (печатается в PDF)
components/                — UI-компоненты и админ-виджеты
lib/                       — supabase-клиенты, типы, расчёт цены, утилиты
supabase/schema.sql        — SQL-схема, RLS-политики, storage bucket'ы
supabase/seed.sql          — тестовые данные (необязательно)
```

## 1. Настройка Supabase

1. Создайте проект на [supabase.com](https://supabase.com).
2. В **SQL Editor** выполните файл `supabase/schema.sql` — он создаст:
   - таблицу `orders` (заказы на всех стадиях: замер → производство → история);
   - таблицу `calculator_settings` (цены, коэффициенты, подарки, текст КП);
   - политики RLS (клиенты видят только активные/готовые заказы, менеджеры — всё);
   - storage bucket'ы `sketches` и `finished-photos`.
3. (Необязательно) выполните `supabase/seed.sql`, чтобы добавить тестовые заказы.
4. Создайте пользователя-менеджера: **Authentication → Users → Add user** (email + пароль).
   Именно этими данными менеджер будет входить на `/login`.
5. Скопируйте `Project URL` и `anon public key` из **Project Settings → API**.

## 2. Настройка проекта

```bash
cp .env.example .env.local
```

Заполните `.env.local`:

```
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-key
```

Установите зависимости и запустите локально:

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000).

## 3. Деплой на хостинг (рекомендуется Vercel)

1. Загрузите этот проект в GitHub-репозиторий.
2. На [vercel.com](https://vercel.com) → **Add New Project** → выберите репозиторий.
3. В **Environment Variables** добавьте те же `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
4. Нажмите **Deploy**.

Проект также работает на любом хостинге с поддержкой Node.js (Next.js standalone):
`npm run build && npm run start`.

## 4. Как пользоваться

- **Лендинг (`/`)** — клиенты рассчитывают стоимость и переходят в "Производство онлайн".
- **`/production`** — публичная страница, видно всем: карточки активных заказов, отсортированные по ближайшей дате монтажа.
- **`/production/[id]`** — открывается по клику на карточку, показывает клиенту только эскиз, дату и статус "В работе".
- **`/login`** — вход для менеджера/монтажника (учётная запись из Supabase Auth).
- **`/admin/zamery`** — менеджер добавляет заявку; кнопки "Согласовали" (→ в производство) / "Потеряли" (→ архив).
- **`/admin/production`** — та же очередь, что видят клиенты, но с полными данными; кнопка "ГОТОВО" открывает окно загрузки фото готовой работы и переносит заказ в историю.
- **`/admin/history`** — поиск по названию компании / телефону, фото готовых работ.
- **`/admin/settings`** — цены калькулятора, коэффициенты, подарки, текст и срок действия КП.

## 5. Коммерческое предложение (КП)

`/api/kp` генерирует красиво оформленную HTML-страницу с расчётом, сроками,
гарантией, QR-кодом и предложением, действующим 12 часов — она автоматически
открывает системное окно печати, так что клиент (или менеджер) может сохранить
её как PDF через "Сохранить как PDF" в диалоге печати браузера.

Если нужен PDF-файл, генерируемый на сервере без участия пользователя, эту
функцию можно расширить с помощью библиотеки `@react-pdf/renderer` или
headless-браузера (Puppeteer) — текущая реализация нарочно оставлена лёгкой,
без зависимости от headless-браузера на хостинге.

## 6. ERP-модуль (заявки, калькулятор, планировщик, монтаж, клиенты)

Поверх базовой системы добавлена ERP-логика:

- **Создание заявки** (`/admin/zamery` → «Создать заявку»): ветка «Требуется замер» (короткая форма) или «Замер не требуется» (полная форма). Клиент определяется по телефону автоматически.
- **Калькулятор внутри заявки**: кнопка «Добавить работу» открывает тот же калькулятор «Световые буквы на каркасе», что и на лендинге (`components/main-calculator.tsx` → `LightLettersOnFrameCalculator`, один код на оба места). Остальные типы изделий — заглушки «В разработке». Позиций в заявке — сколько угодно.
- **Планировщик** (`lib/scheduler.ts`): по нормативам времени и текущей загрузке цеха подбирает ближайшую дату изготовления, учитывая график (пн–чт — вывески, пт–сб — мелкие изделия), плюс один день сверху. Воскресенье в автоподборе не используется — это ручной резерв, менеджер при необходимости выставляет дату сам.
- **Производственный календарь** (`/admin/production`): заказы сгруппированы по неделям с горизонтальной прокруткой внутри строки, вместо плоского списка.
- **Монтаж**: расчёт по городам (Тараз — сложность, Шымкент/Алматы — фиксированная цена), x2 за воскресенье по инициативе клиента, доплата за срочность мелких заказов вне пт/сб — все цифры редактируются в Настройках → «Изделия и монтаж».
- **Клиенты** (`/admin/clients`): карточка клиента с суммой всех его заявок за всё время (`client_totals` view в базе).

### Миграции для выполнения (по порядку, в SQL Editor Supabase)
1. `supabase/schema.sql` — базовая схема (если ещё не выполняли)
2. `supabase/migrations/002_erp_foundation.sql` — клиенты, типы изделий, заявки, позиции работ
3. `supabase/migrations/003_secure_client_totals.sql` — закрытие view с финансами от анонимного доступа
4. `supabase/migrations/004_erp_stage2.sql` — публичный доступ к активным заявкам + перенос старых тестовых заказов из `orders` в новую структуру

### Осознанные упрощения этого этапа
- Норматив для «Алюкобонд с объёмными буквами» — временная заглушка (в ТЗ отдельная цифра не была дана), помечена `needs_review = true`, видна в Настройках жёлтой пометкой. *(Актуально только для старого справочника `product_types`, удалённого миграцией 016 — сейчас не применяется ни к одному живому калькулятору.)*
- Правило «воскресенье как резерв, если недельный план не выполнен» — в планировщике не считается автоматически (потребовалось бы отдельно считать выполнение недельного плана); воскресенье просто исключено из автоподбора, менеджер прописывает его вручную при необходимости.
- Сложность монтажа (лёгкий/средний/сложный) выбирается менеджером вручную при добавлении работы, как и было решено.

## 8. Модуль «Сотрудники, регламент, техкарты»

- **Сотрудники** (`/admin/staff`) — список, статус, назначение ролей. Личный логин создаётся вручную в Supabase Authentication (как для менеджера), затем привязывается к сотруднику по `auth_user_id` (можно сделать прямым SQL-запросом: `update employees set auth_user_id = '<uuid из auth.users>' where id = '<id сотрудника>'`).
- **Роли и оплата** (`/admin/roles`) — способ начисления (фикс/% /почасовая) и ставка, редактируется без кода.
- **Технологические карты** (`/admin/templates`) — цепочки операций по типу изделия с зависимостями (`depends_on_keys`) и флагом «параллельно». При добавлении работы в заявку операции создаются автоматически.
- **Личный кабинет сотрудника** (`/staff`) — свои операции (начать/завершить) и история начислений. Доступен по тому же логину, что и `/admin`, но показывает только то, что относится к этому сотруднику.
- **Зарплатный фонд** (`/admin/payroll`) — начисления по каждому завершению операции (автоматически, триггером в базе), выплата — вручную, одной кнопкой на сотрудника.
- **Закупки** (`/admin/procurement`) — еженедельный чек-лист с ручным вводом нужного количества, кнопка печати.
- **Регламент** (`/admin/regulations`) — чек-лист понедельника (общий на компанию), статус недельного плана (автоматически: все заявки с монтажом на этой неделе завершены?), корпоративные события.

### Миграции для этого модуля (по порядку)
6. `supabase/migrations/006_staff_payroll_foundation.sql`
7. `supabase/migrations/007_operations_triggers.sql`

### Важная оговорка по правам доступа
Раздел заявок (`requests`/`order_items`) пока остаётся открытым для любого авторизованного пользователя — то есть монтажник технически может зайти в `/admin/zamery` и `/admin/production`, хотя интерфейс для него не предназначен. Чтобы закрыть это по-настоящему, нужно ввести отдельный признак «менеджер» (сейчас есть только `is_admin`) и переписать политику доступа к заявкам под него — это следующий логичный шаг, если понадобится.

## 9. Дизайн

Палитра: белый, светло-серый градиент (`bg-mist-gradient`), тёмно-синий
(`navy-900`), синий градиент (`bg-blue-gradient`). Везде — карточки, без таблиц,

## 10. Производственный диспетчер

`/admin/dispatcher` — автоматический расчёт производственного плана по регламенту компании:

- **Производственные дни** — понедельник/среда/пятница (2 объекта/день, эскалация до 3, если на
  неделе получается больше 6, жёсткий потолок 3/день и 9/неделю, переполнение уходит на следующую
  неделю). **Монтажные дни** — вторник/четверг/суббота (день после производственного). Воскресенье
  автоматически становится рабочим, если план недели (заявки этой недели, `status = 'done'`) не
  закрыт — та же логика, что уже выводится в «Регламенте».
- **Объект очереди = заявка целиком** (`requests`), а не отдельная позиция калькулятора. Диспетчер
  сам считает `production_day`/`install_date`, менеджер может переопределить (флаг
  `manual_override` — тогда дата закреплена и алгоритм её не двигает, но учитывает в загрузке дня).
- **Универсальная цепочка этапов** (`lib/dispatcher.ts`, `STAGE_DEFS`): Дизайн → Печать
  букв/Фрезеровка (параллельно) → Сварка/Покраска (параллельно) → Пайка/Сборка (параллельно) →
  Монтаж или Отправка (выбирается полем `fulfillment_mode` в карточке заявки). Хранится в
  `order_operations` (та же таблица и триггеры автоблокировки, что и раньше, только строки теперь
  привязаны к `request_id`, а не только к `order_item_id`).
- **Компетенции сотрудников** (`employee_competencies`) — по регламенту у каждого сотрудника свой
  ранжированный список этапов; на свободную операцию назначается сотрудник с наивысшей
  компетенцией (наименьший ранг), при равенстве — менее загруженный. Свободный сотрудник без своей
  задачи автоматически доназначается на самый загруженный участок из своих компетенций.
- **Срочные заказы** (флаг «Срочно» в карточке заявки) — очередь не меняется, в отчёте дня
  показывается пометка о дополнительной смене 20:00–23:59 для этого объекта.

### Цены калькулятора теперь редактируются в `/admin/settings`
Раньше все цены «Световых букв на каркасе» (₸/мм, глубина, множители типа
свечения, LED/блоки питания, каркас, монтаж/доставка, наценка
«Изготовление», срочность) были захардкожены в `lib/light-letters-pricing.ts`
— поменять цифру можно было только правкой кода. Теперь они хранятся в
`production_settings.light_letters_pricing` (`lib/dispatcher.ts` тут ни при
чём — это отдельная от диспетчера конфигурация) и редактируются формой
`components/admin/pricing-settings-board.tsx` без деплоя. Лендинг (`/`) и
калькулятор внутри заявки — **один и тот же код** (`LightLettersOnFrameCalculator`),
поэтому цены везде одинаковые. Старая независимая формула лендинга
(`lib/pricing.ts`, таблица `calculator_settings`, `/api/calculate`) была
мёртвым кодом (нигде не вызывалась) и удалена миграцией 022.

### Осознанные упрощения этого этапа
- Объект очереди — заявка целиком, даже если внутри неё несколько позиций калькулятора; сейчас это
  соответствует реальности (единственный рабочий калькулятор — «Световые буквы на каркасе»), при
  появлении новых типов изделий цепочку этапов можно будет уточнить.
- Мазлов не участвует в автораспределении диспетчера (в регламенте компетенций для него нет) —
  просто не заведена ни одна строка в `employee_competencies`.
- Доп. смена 20:00–23:59 для срочных заказов — это пометка в отчёте дня, отдельного учёта часов и
  зарплаты за неё пока нет.
- Перенос объектов между неделями считается по производственным дням (пн/ср/пт); внутринедельный
  перенос между производственными и монтажными днями (если объект не успели закончить за один
  производственный день) отдельно не моделируется.
